# 二、七大模块优化设计

## 1. 地图模块 → 分层加载的区域级地图

### 方案分析

| 方案 | 优势 | 劣势 | 结论 |
|------|------|------|------|
| 全国地图 | 可扩展 | 无效区域大、加载慢 | ❌ |
| 陕西锁定 | 聚焦业务、加载快 | 扩展需改代码 | ⚠️ 短期可用 |
| **分层加载** | 默认陕西、支持zoom到全国 | 实现略复杂 | ✅ **推荐** |

### 实现方案

```
Layer 1: 陕西行政区划底图 (GeoJSON, 一次性加载, <50KB)
Layer 2: 风机点位图层 (MarkerCluster聚合, >50台时自动聚合)
Layer 3: 风场热力图 (基于HI值, ECharts heatmap叠加)
Layer 4: 实时风场粒子 (Wind field particles, Canvas/WebGL)
Layer 5: 运维路线 (OSRM路径规划, 显示到故障风机的路线)
```

**技术选型**：
- 底图: `MapLibre GL JS` (免费, 支持矢量瓦片, 比Leaflet性能和交互好10倍)
- 瓦片: 自建陕西矢量瓦片 (使用`tippecanoe`从GeoJSON生成.mbtiles, <5MB)
- 聚合: `supercluster` 做点位聚合, 50+风机时性能不下降
- 热力图: ECharts `heatmap` + Leaflet/MapLibre overlay

**性能优化**：
```
- 初始加载: 只加载可视区域风机 (<20台) → 可视区域外懒加载
- WebWorker: 数据聚合/筛选放Worker线程, 不阻塞UI
- 瓦片缓存: Service Worker缓存底图, 二次打开 <1秒
- 虚拟列表: 风机列表 >100台时虚拟滚动
```

**实现步骤**：
1. 替换Leaflet为MapLibre GL JS
2. 制作陕西矢量瓦片 (tippecanoe + 陕西GeoJSON)
3. 实现三层 MarkerCluster
4. 添加风场粒子层
5. Service Worker缓存

### AI能力设计

**CV模型架构**：
```
YOLOv8-seg (实例分割) + EfficientNetV2 (分类) + ViT (细粒度)
├─ YOLOv8-seg: 检测损伤区域 + 分割mask (mAP@0.5 > 0.85)
├─ EfficientNetV2: 损伤类型分类 (裂纹/腐蚀/脱层/积污 4类)
└─ ViT: 严重程度评级 (轻微/中度/严重 3级)
```

**推理流程**：
```
上传图像
  → 预处理 (CLAHE增强 + 尺寸归一化 640×640)
  → YOLOv8 检测损伤区域 → bbox + mask
  → ROI裁剪 → EfficientNetV2 分类 → 损伤类型 + 置信度
  → ViT 严重程度评估 → 1-3级
  → 结构化输出 {type, confidence, severity, bbox, mask, recommendation}
  → 前端Canvas标注叠加显示
  → 写入诊断记录 (PostgreSQL)
  → 如有相似案例, Milvus检索相似图像
```

**技术实现**：
- 模型部署: ONNX Runtime或TensorRT加速 (GPU推理 <200ms/图)
- 训练数据: 公开风电叶片数据集 + 数据增强 (翻转/旋转/光照变化/雾霾模拟)
- 定期更新: 每月回灌新标注数据, 增量训练

### 数据结构设计

```python
# 工单到日历的映射
class MaintenanceEvent:
    id: int
    turbine_id: int
    turbine_name: str
    workorder_id: int
    event_type: str  # "repair" | "inspection" | "replacement" | "routine"

    title: str
    description: str
    assignee: str
    start_date: datetime
    due_date: datetime       # DDL截止日期
    estimated_hours: float
    status: str              # "scheduled" | "in_progress" | "completed" | "overdue"
    dependencies: list[int]  # 依赖的其他事件ID
    color: str               # 日历显示颜色

# 前端日历数据fetch
GET /api/calendar/events?start=2026-05-01&end=2026-05-31

### 实现方案

1. **日历组件**: 使用 `FullCalendar` (成熟稳定, 支持月/周/日/列表视图)
2. **颜色编码**: 紧急=红 / 计划=黄 / 例行=蓝 / 完成=绿
3. **交互**: 点击事件→弹出工单详情卡片; 拖拽可调整日期
4. **数据同步**: 工单创建/更新时自动同步到`MaintenanceEvent`表
5. **RUL联动**: RUL预测结果 < 阈值时自动在日历中标记预警窗口

  │        │         │         │         │         │
  └────────┴─────────┴─────────┴─────────┴──── 关闭 ──→ [归档]
           │                              │
           └──── 退回 (任意节点) ←─────────┘

状态流转规则:
- 创建: 任何人 → 填写故障/风机/描述 → 自动分配优先级
- 待分配: 系统管理员 → 指派责任人 + 预估工时
- 执行中: 责任人 → 开始维修 → 记录实际工时
- 待验收: 责任人 → 提交完修 → 等待PO/管理员验收
- 已完成: PO/管理员 → 验收通过 → 记录实际成本
- 关闭: 自动 → 30天后归档
```

### 优先级机制

```
优先级 = f(故障严重度, RUL紧急度, 风机重要性)

严重度权重:
  - 停机故障: 10分
  - 性能衰减: 7分
  - 预警信号: 4分
  - 例行维护: 1分

RUL紧急度:
  - < 7天: ×3
  - < 30天: ×2
  - < 90天: ×1
  - > 90天: ×0.5

风机重要性 (按功率):
  - 5MW+: ×1.5
  - 3MW: ×1.0
  - 2MW: ×0.8

优先级: >=20分 → urgent; >=10分 → high; >=5分 → medium; <5 → low
```

### RAG技术架构

```
文档上传
  → 格式解析 (PyPDF2/OpenCV OCR/python-docx)
  → 文本清洗 + 结构化提取
  → 语义分块 (LangChain RecursiveCharacterTextSplitter, chunk_size=512, overlap=64)
  → Embedding (BAAI/bge-large-zh-v1.5, dim=1024)
  → 存储到Milvus (索引: IVF_FLAT, nlist=1024)

检索流程:
  user_query
  → 查询改写 (LLM扩展关键术语: "齿轮箱问题" → "齿轮箱 故障 振动 温度 磨损")
  → 混合检索:
      ├─ 向量检索 (Milvus ANN, top_k=20)
      └─ 关键词检索 (BM25, top_k=10)
  → 融合排序 (RRF: Reciprocal Rank Fusion)
  → 重排序 (BGE-Reranker-v2)
  → Top 5 → 注入LLM Prompt

与AI助手融合:
  Copilot Agent接收用户问题
  → 判断是否需要检索知识库
  → 需要: 触发RAG检索 → 得到Top5文档片段
  → 将片段注入System Prompt: "参考以下知识库片段回答..."
  → LLM生成带引用的回复
```

### 实现技术栈

```yaml
向量数据库: Milvus (自建) 或 Zilliz Cloud
Embedding: BAAI/bge-large-zh-v1.5 (1024维)
分块策略: LangChain RecursiveCharacterTextSplitter
重排序: BGE-Reranker-v2-m3
文档解析: 
  PDF: PyPDF2 + pdfplumber
  Word: python-docx
  Excel: openpyxl + pandas
  Image: OCR (PaddleOCR)
```

# 三、AI能力整体设计

## 三层AI架构

```
Layer 3: Agent层 — Copilot悬浮窗
  ├─ 页面感知 + 多轮对话 + RAG检索 + 工具调用
  └─ 模型: GPT-4o / DeepSeek-V3 / Qwen-Plus (可切换)

Layer 2: 诊断层 — 专业AI模型
  ├─ CV: YOLOv8-seg + EfficientNetV2 → 叶片损伤检测
  ├─ 时序: Informer/PatchTST → RUL预测
  ├─ 信号: 1D-CNN + Transformer → 振动故障分类
  └─ 决策: XGBoost + SHAP → 故障根因排序

Layer 1: 数据层 — 特征工程
  ├─ SCADA特征提取 (统计/频谱/趋势特征)
  ├─ 振动特征提取 (RMS/Kurtosis/FFT峰值/包络谱)
  ├─ 图像特征 (CNN backbone → 特征向量)
  └─ 气象特征 (风速/湍流/温度序列)
```

## 数据流

```
数据源 (SCADA/振动/图像/气象)
  → Kafka消息队列
  → 流处理 (Apache Flink或Python async批处理)
  → 特征提取 (Layer 1)
  → 模型推理 (Layer 2, ONNX Runtime)
  → 结果写入: PostgreSQL (结构化) + Milvus (向量)
  → Agent (Layer 3) 通过Tool Use API查询
  → 前端展示 + Copilot对话
```

# 四、工业级功能扩展清单 (>=10条)

### 1. 数字孪生3D可视化
- **问题**: 2D地图无法呈现风机结构关系和部件状态
- **方案**: Three.js构建3D风机模型, 实时映射SCADA数据到部件颜色(齿轮箱/发电机/轴承温度热力图)
- **集成**: 单机详情页新增3D视图Tab, WebSocket实时推送渲染数据

### 2. 多风场管理
- **问题**: 当前只支持单个地理区域
- **方案**: 地图支持风场切换 (列表 + 收藏), 全局KPI跨风场对比
- **集成**: 导航栏新增风场选择器, 后端API多租户隔离

### 3. 告警规则引擎
- **问题**: 当前只有固定HI阈值告警
- **方案**: 可配置规则引擎 (滑动窗口/组合条件/趋势告警), 例如"HI连续3天下降>5%且振动RMS>3.0"
- **实现**: 自研规则引擎或集成Drools, 规则可视化编辑器

### 4. 移动端适配
- **问题**: 运维人员在现场无法访问系统
- **方案**: React Native或PWA, 核心功能: 接收工单/扫码查风机/拍照上传叶片图/离线缓存
- **集成**: 共享后端API, 移动端专用轻量Dashboard

### 5. 备件库存管理
- **问题**: 维护计划生成后无法确认备件可用性
- **方案**: 备件库存模块: 入库/出库/预警/供应商管理/自动采购建议
- **集成**: 与工单系统联动, 创建工单时自动检查库存, 不足时生成采购单

### 6. 运维人员排班系统
- **问题**: 工单分配给谁? 谁有空? 谁离风机近?
- **方案**: 排班日历 + 技能矩阵 + 地理位置, 工单自动推荐最佳责任人
- **实现**: 工单分配算法 (匈牙利算法), 排班冲突检测

### 7. 报告自动生成
- **问题**: 管理者需要定期运维报告(周报/月报/季报)
- **方案**: LaTeX/HTML模板引擎, 自动填入数据 (KPI/故障/成本), 导出PDF
- **实现**: Jinja2模板 + WeasyPrint/Playwright PDF渲染

### 8. 多语言支持 (i18n)
- **问题**: 未来可能服务海外风场
- **方案**: react-i18next + 后端Babel, 先做中英文
- **实现**: JSON翻译文件, 动态切换

### 9. 审计日志
- **问题**: 谁改了配置? 谁创建了工单? 无法追溯
- **方案**: 全量审计: 用户操作 → Kafka → ClickHouse
- **实现**: 中间件拦截所有POST/PUT/DELETE, 异步写入

### 10. API开放平台
- **问题**: 第三方系统无法对接 (如ERP/SCM)
- **方案**: OpenAPI规范 + API Key管理 + 限流 + 文档
- **实现**: FastAPI自带OpenAPI, 加API Key中间件 + Redis限流

### 11. 风功率预测
- **问题**: 只有设备健康管理, 没有发电预测
- **方案**: 基于气象数据 + 历史功率的时序预测 (TFT/Informer模型)
- **价值**: 帮助风场做发电计划, 电网调度

### 12. 碳减排核算
- **问题**: 缺少ESG/碳减排数据
- **方案**: 根据发电量自动计算碳减排量 (相对于火电基准线)
- **集成**: Dashboard新增碳减排KPI卡片
