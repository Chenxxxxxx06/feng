### 4. 执行原则

1. 先复现，再修复；先修根因，再修表象。
2. P0 优先，但不要把“修完所有低价值 P1”作为创新闭环的前置条件。
3. 每项实现必须有可执行验收，不接受“代码看起来完成”。
4. LLM 只负责理解、解释、生成建议和编排；状态变更、权限、安全门禁和关键计算必须由确定性代码控制。
5. 所有写操作都必须具备权限检查、参数验证、幂等键、状态机约束、审计记录和可恢复失败路径。
6. 不伪造准确率、节省成本、告警压缩率、RUL 提升等指标；指标必须来自可重复测试或演示记录。
7. 数据库结构变更必须通过正式迁移完成，不允许依赖应用启动时临时 `ALTER TABLE`。
8. 不为了“炫技”重写整个技术栈；优先复用现有代码，做最小、清晰、可验证的结构改造。
9. 未经授权不得连接或控制真实风机、PLC、SCADA 或 OPC UA 写端。
10. 遇到一般实现选择时自行作出最保守的合理决定并记录；只有涉及外部权限、真实设备写入、不可逆数据变更或赛题方向重大改变时才询问用户。

### 7. 阶段 1：修复可信运行基础

按问题清单顺序优先解决：

1. Fault 模型与运行时字段不一致。
2. 正式数据库迁移与模型同步。
3. 后端测试收集、stdout 污染和 SQLite 隔离。
4. RUL 功率阈值、紧急度插值等确定性算法错误。
5. 调度器人员数量、工时和容量约束。
6. 工单、故障、维护任务的非法状态跳转。
7. 关闭/恢复验证条件。

每个问题执行：

```text
复现失败 → 添加或修正测试 → 最小修复 → 相关测试 → 全量回归 → 更新台账
```

状态机至少覆盖：

```text
detected
→ triaged
→ diagnosed
→ planned
→ approval_required / approved
→ executing
→ verification
→ resolved / rolled_back / escalated
```

非法转换必须返回稳定的业务错误；不能只靠前端隐藏按钮。

#### 阶段退出条件

- 所有 P0 算法和状态一致性问题都有回归测试。
- 后端完整测试可正常收集和结束。
- 不再依赖启动时临时改表。
- 关键状态转换可验证、可审计。

### 8. 阶段 2：安全与权限边界

优先解决：

1. 注册接口角色提升。
2. 后端真实 RBAC，而不是仅前端菜单权限。
3. inactive 用户访问。
4. JWT 固定密钥和生产配置 fail-fast。
5. API Key 泄露、明文返回和日志输出。
6. Agent 写操作的审批、幂等与并发竞态。
7. 上传类型、大小、路径和内容校验。
8. 认证、Agent 和高成本端点的速率限制。

至少建立角色：

```text
viewer
operator
engineer
approver
admin
```

高风险动作至少要求：

```text
服务端权限检查
+ 策略引擎判定
+ 明确审批
+ 幂等键
+ 审计记录
+ 可回滚或失败补偿
```

#### 阶段退出条件

- 权限绕过、角色提升、inactive 用户和密钥暴露测试通过。
- LLM 输出不能绕过确定性策略直接写业务状态。
- 并发确认不会重复执行。
- 生产环境缺失关键密钥时拒绝启动，而不是静默使用默认值。

### 9. 阶段 3：统一 Agent 主链

把分散、重复或互相冲突的 Agent 流程收敛到一条可观察主链：

```text
事件输入
→ 告警聚合
→ 证据收集
→ 诊断假设
→ 方案生成
→ 策略评估
→ 人工审批
→ 工单/调度执行
→ 恢复验证
→ 事件关闭
→ 复盘沉淀
```

要求：

- 每次运行有 `trace_id`、`incident_id`、步骤序号、输入摘要、输出摘要、耗时、工具调用、策略结果、审批人和最终状态。
- LLM 调用失败、超时、结构化输出错误时有确定性降级路径。
- 同一事件重复提交时可识别并合并，不生成重复工单。
- Agent 不能将“文本确认”误当成真实执行成功。
- 统一错误模型和错误码。

#### 阶段退出条件

- 一个固定演示事件可以从输入走到关闭。
- 中途任一步失败后能够重试、升级或回滚，不丢失审计链。
- 飞行记录可按 `incident_id` 完整回放。

### 10. 阶段 4：比赛核心创新 MVP

实现顺序必须是：

#### 4.1 自主运维事件指挥官

建立一等领域对象 `Incident`，将故障、告警、诊断、方案、审批、工单、执行、验证和复盘串成一个事件，而不是多个互不关联的页面。

#### 4.2 告警风暴压缩

用可解释规则完成第一版：

- 时间窗
- 同一风机/部件
- 告警共现
- 上下游依赖
- 严重度
- 重复抑制

输出“一个事件 + 告警簇 + 主告警 + 被合并依据”。必须保存压缩前后数量和规则证据。

#### 4.3 因果证据图

区分：

- 观测事实
- 规则推断
- 模型预测
- LLM 假设
- 人工结论

每条边必须携带来源、时间、置信度和可回溯引用。UI 上不能把假设伪装成事实。

#### 4.4 反事实维修决策沙盘

至少比较三个可执行方案，例如：

- 立即停机维修
- 降载运行后计划维修
- 继续监测并设置触发阈值

使用确定性评分卡比较安全风险、停机损失、人员/备件可用性、预计恢复时间和策略约束。LLM 负责解释，不负责决定分数。

#### 4.5 工业安全策略引擎

实现可测试的策略规则：

- 哪些动作可自动执行
- 哪些必须审批
- 哪些条件下禁止执行
- 哪些异常必须升级
- 哪些执行结果必须进入验证

Demo 必须展示至少一次策略拒绝或要求人工审批，而不是永远“一键通过”。

#### 4.6 Agent 飞行记录器

提供事件时间线和步骤回放，能够回答：

- 当时看到了什么证据？
- 为什么选择这个方案？
- 哪条策略要求审批？
- 谁批准了什么？
- 执行后如何确认恢复？

#### 创新 MVP 退出条件

- 上述六项形成同一个闭环，不是六个静态页面。
- 事件刷新后仍可恢复，不能只存在内存。
- 同一固定演示场景连续运行 3 次，结果稳定且无重复副作用。
- 指标全部来自日志和测试，不手写“优秀结果”。

5. 策略引擎阻止高风险直接执行并要求审批。
6. 审批后生成工单与调度。
7. 执行结果进入恢复验证。
8. 事件关闭并回放完整飞行记录。

- 前端生产构建通过。

- Demo 场景连续执行 3 次成功。

### 12. OPC UA 范围约束

OPC UA 不是当前 Goal 的必选阻断项。只有核心闭环已经稳定且剩余时间充足时，才实现“数字影子网关”：

- 只读连接或模拟服务器
- 节点浏览与语义映射
- 订阅值变化
- 将变化转换为平台事件
- 断线重连和质量码
- 写操作仅在本地模拟沙箱，并经过策略引擎和审批

不要做完整 OPC 管理平台，不要直接控制真实设备，不要让 OPC 工作拖垮核心 Agent 闭环。

如实现该项，必须用 ADR 说明“为什么做、为什么只做这些、真实生产接入还缺什么”。

| Agent | 超时、错误输出、工具失败、重试、降级和恢复 |
| 前端 | 加载、失败、空状态、权限、审批、回放 |
| E2E | 固定事件从进入到验证关闭的完整闭环 |
| 安全 | 角色提升、越权、inactive、密钥、上传、速率限制 |
| 可访问性 | 键盘、焦点、label、alt、对比度和状态表达 |
| 性能 | 大 bundle、重复请求、事件时间线和图谱渲染 |

每个阶段都运行受影响测试；每个 checkpoint 前运行完整回归。

不能把以下情况标为“通过”：

- 测试未执行
- 只运行了单个 happy path
- 通过 ignore/skip 隐藏失败
- 依赖手工改数据库
- 依赖未记录的本地环境状态
- 结果只存在截图、没有日志或断言

### 14. 本地提交规范

每阶段完成且回归通过后：

1. 检查 `git diff --check`。
2. 使用 `git diff -- <exact files>` 复核。
3. 只暂存本阶段明确文件。
4. 提交信息示例：

```text
fix(domain): enforce incident state transitions
fix(auth): enforce server-side role policies
feat(agent): add auditable incident orchestration
feat(incident): add alarm clustering and evidence graph
test(e2e): verify maintenance closed loop
```

5. 在执行台账记录 commit hash、测试命令和结果。

禁止提交：

- 密钥、token、真实凭据
- `.env`
- 大型模型或数据文件
- 构建产物
- 用户进入任务前的受保护改动

### 15. Definition of Done

只有同时满足以下条件，Goal 才能完成：

- [ ] 当前分支仍为 `codex/goai-wind-ops`。
- [ ] 用户原有未提交改动未被覆盖、删除或混入提交。
- [ ] 问题清单中全部 P0 已修复，或有可复查证据证明条目不成立。
- [ ] 阻断核心闭环的 P1 已修复；剩余 P1/P2 有明确风险和后续顺序。
- [ ] 后端完整测试可收集、可结束并通过。
- [ ] 前端生产构建通过。
- [ ] 核心 API 权限、幂等、并发和状态机测试通过。
- [ ] 关键事件 E2E 通过。
- [ ] 六项核心创新形成同一条可操作闭环。
- [ ] Demo 固定场景连续执行 3 次成功且无重复副作用。
- [ ] 飞行记录器能解释证据、决策、审批、执行和验证。
- [ ] 所有指标可由日志或测试复现，没有编造。
- [ ] ship-gate 无 Critical。
- [ ] 有完整启动说明、环境说明、迁移说明、测试说明和五分钟 Demo 脚本。
- [ ] `docx/CLAUDE执行进度与验收记录.md` 已更新为最终状态。
- [ ] 生成 `docx/CLAUDE最终交付与剩余风险报告.md`。

### 16. 最终交付报告格式

最终不要只说“已经完成”。必须给出：

1. 实现结果概述。
2. 关闭的 P0/P1 编号。
3. 核心创新如何形成闭环。
4. 实际修改文件列表。
5. 数据库迁移列表。
6. 测试命令、通过数、失败数和运行时间。
7. 三次 Demo 回归结果。
8. ship-gate 结果。
9. 本地 commit 列表。
10. 仍未完成的问题、真实原因、风险与建议。
11. 用户下一步只需执行的启动和演示命令。

所有结论必须能回到代码、测试、日志或 commit，不要用空泛表述代替证据。

现在开始：先创建 Goal，检查分支和受保护改动，完整阅读两份文档和比赛要求，建立执行台账，复现基线，然后从 P0 第一批开始持续实施。不要在只完成计划后停下来。
