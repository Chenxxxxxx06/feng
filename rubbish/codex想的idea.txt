结论很明确：现在不要继续横向堆“库存页面、供应商页面、质量页面”。项目已经有足够多的功能名词，真正短缺的是一条自动执行、受安全约束、能够证明结果有效的工业 Agent 主链。

最值得做的方向是把项目重新定义为：

> 风调预顺 WindOps ProofLoop：面向风电运维的“可验证闭环工业 Agent”  
> 不只是告诉用户“可能坏了”，而是证明“为什么判断、为什么这样修、谁批准、修完是否真的恢复”。

这比“又一个风电预测平台”或“多 Agent 聊天系统”更容易形成评委记忆点。

## 一、我检查后的真实完成度

先说好的部分：

- Incident 后端、页面雏形和六个概念已经存在。
- Incident 专项 E2E 为 `4 passed`。
- 全量后端测试实测为 `84 passed / 7 failed`。
- 前端生产构建通过。
- Incident 页面已完成路由接入和基础三栏布局。
- 原有诊断、预测、工单、人员、气象、知识库等能力比较丰富。

但“六项创新已经形成闭环”的说法目前偏乐观，原因如下。

### 1. 决策沙盘实际上还是固定模板

[incidents.py](G:/code/code_vscode/rjcx/feng/backend/app/api/incidents.py:548) 中三个维修方案基本为固定值：

- 人员永远可用
- 备件永远可用
- 天气永远兼容
- 安全风险固定为 5%、20%、45%
- 维修成本和恢复时间按固定倍数计算
- 所谓 LLM explanation 也是预先写好的文本

这还不是“反事实决策”，只是根据事件严重度调整固定方案。

### 2. 安全策略没有真正卡住执行

[事件状态转换接口](G:/code/code_vscode/rjcx/feng/backend/app/api/incidents.py:211) 只检查状态是否合法，没有调用策略引擎，也没有检查：

- 是否已经审批
- 是否有足够证据
- 是否完成恢复验证
- 是否具备备件、人员和天气窗口
- 当前用户是否有该具体动作的审批权

因此用户可以先调用策略检查看到“拒绝”，然后直接调用状态转换进入 `resolved`。现有 E2E 测试也是这样操作的：[e2e_test_incident_closed_loop.py](G:/code/code_vscode/rjcx/feng/backend/tests/e2e_test_incident_closed_loop.py:133)。

这在评委看来会是“策略展示组件”，而不是“工业安全策略引擎”。

### 3. 飞行记录器目前是空记录

全仓库没有真实创建 `AgentSpan` 的业务代码。现在只是手动点击“飞行记录”，创建一个：

```text
status=running
total_spans=0
```

并且是在整个业务流程结束后才创建。[start_agent_trace](G:/code/code_vscode/rjcx/feng/backend/app/api/incidents.py:920) 没有记录之前发生的诊断、工具调用、策略决策和状态变更。

### 4. 因果证据图需要用户手动“造证据”

Incident 页面点击“添加证据”后，会写入固定的：

```text
振动RMS异常 + 当前时间 + confidence=0.9
```

参见 [IncidentPage.tsx](G:/code/code_vscode/rjcx/feng/frontend/src/pages/Incident/IncidentPage.tsx:147)。

证据没有自动来源于：

- SCADA 记录
- 振动频谱
- RUL 预测
- 历史工单
- 故障知识图谱
- YOLO 检测
- Agent 工具调用

所以它现在是“用户填写的节点列表”，不是因果推理结果。

### 5. 告警风暴压缩仍然比较表层

[告警压缩算法](G:/code/code_vscode/rjcx/feng/backend/app/api/incidents.py:261) 虽然接收 `window_minutes`，但没有真正读取告警发生时间并应用时间窗口。

同时，从 Fault 和 WorkOrder 转换的告警都把 `component` 设置为 `None`，导致“同部件”和“上下游部件依赖”很难真正生效。

### 6. Incident 与原有 Agent 系统没有接起来

Incident 模块之外没有其他 Agent、诊断、工单服务引用 `Incident`。也就是说：

- 原来的多 Agent 诊断不会自动创建 Incident
- Incident 不会调用现有诊断 Orchestrator
- 决策方案不会调用维护排程器
- 状态推进不会自动创建工单
- 飞行记录不会记录原有 Agent 工具调用
- 工单结束不会触发 Incident 恢复验证

现在实际是“已有系统旁边新放了一个 Incident 子系统”。

### 7. 前端还有两个直接影响 Demo 的状态问题

例如决策沙盘生成后：

```tsx
setPlans(sb.plans);
selectIncident(selected);
```

但 `selectIncident()` 随后会执行 `setPlans([])`。告警压缩也存在相似问题。因此接口明明成功，结果却可能立即被异步刷新清空。

### 8. 文档与实测存在差异

- 文档有地方写 `84 passed / 0 failed`
- 实际全量测试是 `84 passed / 7 failed`
- 文档声称 ship-gate 已完成，但另一份报告又写“需运行审计”
- Incident 前端页面目前仍是未跟踪文件，尚未进入提交

因此当前更准确的判断是：

> 工程基础已经明显改善，但创新仍处于“API 原型 + UI 原型”阶段，还没有进入可答辩的工业闭环阶段。

如果现在直接参赛，我对整体得分的保守估计是约 55–65 分；最大丢分会发生在 Agent 闭环、安全真实性和 Demo 深度，而不是功能数量。

## 二、真正值得冲高分的核心创新

比赛官方强调真实用户、真实业务流程、可运行且可验证的任务闭环，明确不鼓励泛聊天和概念展示；工业方向重点包括设备、工单、库存、排产和供应链协同，但至少完成一个足够深的闭环即可。[GOAI 官方赛题页](https://www.goaihz.com/en/tracks?track=apps)

所以我建议把所有创新收敛成一条“黄金主链”：

```text
异常发生
→ Agent自动调查
→ 形成可追溯证据包
→ 生成受资源约束的维修方案
→ 策略引擎强制审批
→ 生成携带证明的工单
→ 执行后自动验证恢复
→ 签发恢复证明
→ 沉淀为可复用案例
```

### 创新一：自主调查编排器

当前五个按钮应升级成一个“启动自主调查”按钮。

Agent 自动完成：

1. 读取风机运行上下文。
2. 收集最近告警与异常信号。
3. 调用振动诊断。
4. 查询 RUL。
5. 查询相似历史故障和维修手册。
6. 检查是否已经存在关联工单。
7. 构建根因候选和证据图。
8. 判断是否还缺必要证据。
9. 生成维修方案。
10. 进入审批或升级。

页面展示实时 DAG：

```text
✓ 收集SCADA
✓ 分析振动频谱
✓ 查询历史案例
✓ 生成根因候选
⚠ 缺少齿轮箱油液检测
○ 等待工程师确认
```

这才能体现真正的任务理解、规划、工具调用和异常处理。

### 创新二：证据契约——Proof-Carrying Incident

这是我认为最有辨识度的创新。

每个 Incident 定义一份“证据契约”：

```text
要声称“齿轮箱轴承故障”，至少需要：
- 振动频谱对应特征
- SCADA温度/载荷变化
- 排除传感器漂移
- 相似历史案例
- 证据来源和时间
```

系统区分：

- 已验证事实
- 模型预测
- 规则推断
- LLM 假设
- 人工确认
- 冲突证据
- 缺失证据

证据不足时，Agent 不能把“假设”升级为“确诊”。

其产品价值不是“图谱更好看”，而是：

> 每一个工业判断都携带它成立所需的证明。

### 创新三：真实约束驱动的维修决策数字孪生

把现在固定的三方案升级为动态计算：

输入：

- 当前 RUL 和不确定性
- 实际功率及电价假设
- 风机停机损失
- 人员技能和班次
- 当前工单占用
- 天气窗口
- 最小备件库存
- 备件到货周期
- 故障继续发展的风险
- 维修后恢复概率

输出不仅是三个分数，而是：

- 推荐方案
- 置信区间
- 关键假设
- 风险贡献分解
- 方案翻转点
- 缺失信息
- 哪个约束导致方案不可执行

例如：

> 当前推荐“降载至70%，36小时后维修”。  
> 若振动RMS超过11.8 mm/s，或48小时天气窗口取消，推荐立即停机。  
> 该建议对备件到货时间最敏感。

这里不需要建设完整 ERP。只需要做一个最小的“运维资源影子”：

- 备件库存
- 在途数量
- 预计到货时间
- 人员技能
- 人员可用时间
- 天气窗口

### 创新四：策略即执行边界

策略引擎不能只是查询接口，必须进入所有写操作的必经路径：

```text
用户/Agent发起动作
→ 权限检查
→ 风险分级
→ 策略判定
→ 前置条件检查
→ 审批
→ 幂等执行
→ 审计记录
```

至少实现三类真正可演示的安全场景：

1. 证据不足，拒绝确诊。
2. 没有恢复验证，拒绝关闭事件。
3. L3 动作没有审批，拒绝执行。
4. 备件或人员不满足，拒绝启动维修。
5. 模型建议与安全规则冲突，安全规则优先。

策略可以继续使用现有轻量规则实现；如果后续需要标准化，可参考 OPA/Rego 的“策略即代码”思路，将结构化输入交给声明式策略判断。[Open Policy Agent 官方文档](https://www.openpolicyagent.org/docs/policy-language)

### 创新五：恢复证明，而不是“关闭按钮”

这会成为整个项目最有价值的结尾。

工单完成后系统自动进入观察窗口，比较：

- 维修前后振动 RMS
- 关键频带能量
- 温度
- 功率稳定性
- 告警是否复发
- 健康指数
- 预测 RUL
- 观察时间是否充分

最后生成“恢复证明”：

```text
恢复状态：有条件通过
观察窗口：6小时
振动RMS：14.8 → 6.2 mm/s
齿轮啮合频率能量：下降52%
温度：稳定在62–66℃
重复告警：0
剩余风险：观察窗口不足24小时
建议：保持降载运行18小时后重新评估
```

如果验证失败，系统自动：

```text
verifying → executing / escalated
```

而不是允许用户关闭。

这非常贴合比赛的“结果交付、验证与反馈”，也会让评委清楚看到：你们的闭环不是流程图，而是真的用结果决定能不能结案。

### 创新六：真实 Agent 飞行记录器

不是自己造一套空表，而是自动埋点记录真实流程：

- Agent 调用
- LLM 调用
- 工具调用
- 检索
- 状态变更
- 策略判定
- 审批
- 异常与重试
- Token、费用和耗时
- 输入输出摘要或哈希

可参考 OpenTelemetry 的 GenAI 语义约定，例如 `invoke_agent`、`execute_tool`、模型、Token 和 Tool Call 属性。[OpenTelemetry GenAI 可观测性](https://opentelemetry.io/blog/2026/genai-observability/)

最终页面要支持：

- 按时间回放
- 展开每一步输入输出
- 查看证据来自哪里
- 查看策略为什么拒绝
- 从某一步“分叉重演”
- 对比两次不同维修方案的结果

“分叉重演”本身就是一个很强的 Demo：

> 如果当时选择继续运行，而不是降载维修，系统预计会发生什么？

## 三、第二梯队创新

### 1. 维修案例记忆与自我校准

不只是把结果存入知识库，而是记录：

```text
当时判断了什么
置信度是多少
实际拆检结果是什么
采取了什么维修措施
维修是否有效
多久后再次故障
```

系统可以持续计算：

- 哪类诊断最准确
- 哪类维修最容易返修
- 哪个置信度区间存在过度自信
- 哪个部件的历史方案成功率最高

这是真正的“Agent 学习闭环”，比普通向量知识库更有说服力。

### 2. 工业 Agent 压力测试与演练中心

内置若干事故演练：

- 传感器突然离线
- 两个传感器互相矛盾
- LLM 超时
- 气象服务不可用
- 备件临时取消到货
- 审批人不在线
- 同一告警重复100次
- 恶意提示要求绕过审批

系统自动评分：

- 是否安全降级
- 是否重复创建工单
- 是否越权执行
- 是否保留审计记录
- 是否正确升级人工处理

评委甚至可以现场选择一个异常注入。这比提前录好的固定 Demo 更能证明技术真实性。

### 3. 最小 OPC UA 数字影子

可以做，但不要做成“大而全 OPC 管理系统”。

最合适范围是：

```text
模拟 OPC UA Server
→ 浏览风机节点
→ 订阅值变化和告警事件
→ 映射成平台 Incident
→ Agent 自动调查
```

只读订阅已经足够体现工业接入真实性。OPC UA 本身支持对变量变化和事件的订阅、过滤和通知机制，适合作为 Incident 的工业事件入口。[OPC UA Subscription](https://reference.opcfoundation.org/specs/OPC-10000-4/5.13.1.1)

进一步可选支持 AAS/资产管理壳导出，使风机、部件、技术参数、维护记录和 Incident 能用标准化数字孪生结构表达。AAS 的目标本身就是提供标准化数字孪生的信息模型和 API。[IDTA AAS 规范](https://industrialdigitaltwin.org/en/content-hub/aasspecifications)

但这两项都是加分项，不能排在主闭环之前。

### 4. 多模态现场验收

让维修人员上传：

- 维修后照片
- 叶片图像
- 振动文件
- 铭牌照片
- 语音描述

Agent 将多模态结果作为“恢复证明”的组成部分，而不是单独做一个图片识别页面。

## 四、明确不要优先做的内容

以下方向投入不少，但不一定提高成绩：

- 完整 ERP、采购或供应链系统
- 单独建设质量管理平台
- 只有 CRUD 的库存页面
- 泛化聊天助手
- 单纯增加 Agent 数量
- 单纯接入向量数据库
- 只有动画效果的数字孪生
- 完整 OPC UA 管理平台
- 更多硬编码演示指标
- 再写一套与业务主链分离的新后端

比赛列出设备、质量、工单、库存、排产和供应链，是方向范围，不是要求每个团队做六个独立子系统。官方核心要求仍然是至少一个可演示、可验证的真实闭环。[官方规则](https://www.goaihz.com/en/tracks?track=apps)

## 五、建议实施顺序

### 第一阶段：把“伪闭环”变成真闭环，3–4天

1. 策略强制进入状态转换。
2. `resolved` 必须具备恢复验证证明。
3. Trace 自动开始，真实写入 Span。
4. 修复 Incident UI 结果自动清空问题。
5. Incident 接入已有诊断 Orchestrator。
6. 事件推进改为后台编排，不再依赖用户逐个点按钮。

### 第二阶段：形成差异化创新，4–6天

1. 证据契约。
2. 自动证据收集和证据冲突。
3. 实际资源约束决策沙盘。
4. 最小备件、人员、天气资源影子。
5. Proof-Carrying Work Order。
6. 自动恢复验证和恢复证明。

### 第三阶段：形成决赛表现力，3–5天

1. Agent 飞行记录时间线。
2. 方案分叉重演。
3. 工业异常演练中心。
4. 相似案例与维修效果反馈。
5. Demo 自动播演模式。
6. 可选 OPC UA 只读数字影子。

## 六、最终五分钟 Demo 应该变成这样

1. OPC 模拟器或 SCADA 触发齿轮箱振动异常。
2. 系统自动将 27 条告警压缩为 1 个 Incident。
3. Agent 自动调用 SCADA、振动、RUL、历史工单和知识库。
4. 因果图显示两个根因候选，其中一个因证据冲突被降权。
5. 决策沙盘发现立即维修受备件到货约束，推荐降载36小时。
6. 用户尝试直接关闭事件，策略引擎真实拒绝。
7. 工程师审批后生成携带证据、资源和验证标准的工单。
8. 模拟维修完成后，系统自动比较维修前后指标。
9. 第一次因观察时间不足显示“有条件通过”，不能关闭。
10. 观察数据补足后签发恢复证明，事件关闭。
11. 飞行记录回放全部工具、证据、决策、审批和验证。
12. 最后切换一个假设：“若选择继续运行”，展示分叉结果。

这套叙事同时覆盖：

- 行业价值
- Agent 自主规划
- 工具调用
- 知识增强
- 多轮状态
- 结果验证
- 安全边界
- 可追溯
- 产品体验
- 技术深度

我按 CPO/CTO 的策略框架做出的最重要调整，就是把“功能覆盖率”换成“一个结构性差异化能力”：可验证工业闭环。北极星指标也建议定为：
