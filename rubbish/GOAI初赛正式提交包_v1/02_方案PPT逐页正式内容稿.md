## Slide 2｜行业问题：工单关闭，不等于设备恢复

### 页面结论

**风电运维的核心断点不是缺少告警，而是缺少可验证的行动闭环。**

### 三个断点

1. **信息断点**  
   SCADA、振动、图像、告警、历史工单分散，告警数量不等于有效事件数量。

2. **决策断点**  
   “立即停机、降载运行、先巡检、继续监测”受人员、备件、天气、RUL 和安全规则共同约束。

3. **验证断点**  
   维修工单可以被人工关闭，但设备是否恢复、风险是否消失、判断依据是否完整，常常缺少机器可核验的证明。

### 典型用户

- 风电场场长：关心安全、停机损失和责任闭环；
- 设备工程师：关心根因、证据和方案可行性；
- 检修班组：关心任务、工具、安全清单和验收标准。

### 不使用的虚假数字

本页不写“某风场每年损失 200 万”“效率提升 80%”等无来源数据。价值通过可计算公式和试点指标验证。

### 视觉指令

用“告警墙 → 人工微信群/表格 → 工单关闭”的断裂流程，对比右侧“事件闭环”。突出红色断点。

## Slide 3｜产品定位：从 PHM 大屏升级为事件指挥系统

### 页面结论

**我们的产品不是“会聊天的运维大屏”，而是可验证闭环工业 Agent。**

### 旧方式与 ProofLoop 对比

| 传统方式 | WindOps ProofLoop |
|---|---|
| 展示传感器和告警 | 将告警组织为 Incident |
| 输出一个故障结论 | 输出证据、缺口、冲突与置信边界 |
| 推荐固定维修模板 | 在资源与安全约束下比较候选方案 |
| 前端弹窗提醒风险 | 服务器端策略网关阻止越权动作 |
| 工单完成即关闭 | 恢复验证通过后才允许关闭 |
| 日志只用于排错 | Agent Trace + 审计链支持复盘 |

### 北极星指标

**可验证事件闭环率 VICR**

已关闭事件中，同时具备最小证据集、审批、执行记录和恢复证明的比例。

### 视觉指令

使用左右对照的“旧系统 / 新类别”框架，中间用一条粗箭头标记产品范式升级。

## Slide 4｜黄金闭环：一个 Incident 贯穿 8 个环节

### 页面主流程

```text
异常进入
→ 告警关联
→ Agent 自主调查
→ 证据契约
→ 决策孪生
→ 策略审批
→ 工单执行
→ 恢复验证
→ 复盘沉淀
```

### 每一步交付物

| 环节 | Agent 行为 | 可验证产物 |
|---|---|---|
| 异常进入 | 接收设备、业务或人工输入 | Incident ID、时间戳 |
| 告警关联 | 时窗、设备、部件、依赖关系聚类 | 告警簇、压缩解释 |
| 自主调查 | 调用 SCADA、振动、RUL、知识库 | 工具调用记录、Evidence |
| 证据契约 | 检查类型、时效、冲突、完整度 | 最小证据集、缺失清单 |
| 决策孪生 | 生成并比较维修候选方案 | 可行性、得分、置信区间 |
| 策略审批 | RBAC、风险、前置条件、策略 | allow / deny / approval |
| 工单执行 | 生成人员可执行任务包 | 工序、安全清单、验收项 |
| 恢复验证 | 比较维修前后指标和告警复发 | 恢复证明、剩余风险 |
| 复盘沉淀 | 记录 Agent 行为与人工反馈 | Trace、审计链、知识草案 |

### 关键边界

**任何数据不足都必须输出 `insufficient_data`，不能用大模型补齐事实。**

### 视觉指令

使用完整闭环环形图，中间放 Incident。每个节点配一个小型“产物卡”，而不是只画箭头。

## Slide 5｜Demo：4 分钟验证一个完整任务，而不是展示菜单

### Demo 样例

**齿轮箱振动异常事件**

### 演示路径

1. 创建或选择一个高风险 Incident；
2. 启动自主调查，展示步骤状态与 Agent Span；
3. 查看证据完整度、缺失证据和来源；
4. 生成 4 个维修候选方案，展示不可行原因与数据质量警告；
5. 尝试跳过验证直接关闭，服务器返回拒绝；
6. 执行恢复验证，展示 `pass / conditional / fail / insufficient_data`；
7. 查看审计链，说明 SHA-256 链与可选 Ed25519 签名；
8. 回到事件状态，证明关闭条件由后端控制。

### Demo 成功标准

- 主流程不是预录动画，按钮触发真实 API；
- 策略拒绝必须能稳定复现；
- 每个结论能点回来源或 Trace；
- 缺数据时展示“不足”，不展示伪造结果；
- 连续演示 3 次不产生重复副作用。

### 视觉指令

采用“操作—Agent—证据—结果”四泳道时序图。右上角标注“可演示、可验证、可复现”。

## Slide 6｜Agent 架构：大模型负责理解，确定性系统负责执行

### 四层架构

1. **交互与事件层**  
   React 事件指挥中心、现场模式、Copilot、工单和诊断页面。

2. **Agent 编排层**  
   Intent Router、Investigation Orchestrator、Data Agent、Knowledge Agent、Synthesizer；10 步可恢复调查工作流。

3. **工具与算法层**  
   SCADA 查询、振动诊断、RUL、知识检索、告警相关性、MCDM 决策、恢复验证、合规检查。

4. **安全与证据层**  
   RBAC、状态机、策略网关、Evidence Contract、Agent Trace、审计链。

### 模型使用边界

- 通义千问 / OpenAI-compatible：意图理解、计划解释、知识提取；
- 统计与规则算法：异常判断、约束检查、状态转换、安全拦截；
- LLM 不可用时：降级到规则和统计流程；
- 比赛版本：禁止直接控制真实物理设备。

### 技术栈

FastAPI、SQLAlchemy Async、Alembic、React、TypeScript、SQLite/PostgreSQL、Qwen/OpenAI-compatible。

### 视觉指令

四层架构图中必须画出一条“LLM 建议 → 策略网关 → 人工审批 → 业务 API”的路径，并用红线阻断“LLM → 设备控制”。

## Slide 7｜创新一：携证事件与证据契约

### 页面结论

**模型不只给答案，还必须说明答案是否够资格进入下一步。**

### Evidence Contract

证据对象至少包含：

- 类型：观察、假设、检查、动作、结果等；
- 来源：SCADA、振动、图像、RUL、知识库、人工；
- 置信度与质量等级；
- 采集时间与新鲜度；
- 支持或反驳关系；
- 数据血缘与关联对象。

### 四个判断

1. **完整度**：最小证据类型是否齐全；
2. **新鲜度**：过期证据是否衰减；
3. **冲突度**：多模态证据是否互相矛盾；
4. **确诊门槛**：未达到门槛时只允许输出候选诊断。

### 与普通 RAG 的区别

RAG 解决“找到相关资料”；Evidence Contract 解决“当前行动是否有足够证据负责”。

### 视觉指令

中心为一个 Incident 证据图，绿色边代表支持、红色边代表反驳、灰色虚线代表缺失证据；右侧显示完整度仪表但不放虚构百分比。

## Slide 8｜创新二：资源约束决策孪生，不给无法执行的建议

### 候选方案

- 立即停机维修；
- 降载运行 + 计划维修；
- 继续监测；
- 先巡检再决策。

### 算法结构

1. 从数据库快照读取 RUL、当前功率、人员技能、活动工单等；
2. 检查人员、备件、天气和安全硬约束；
3. 以安全、经济、资源、恢复时间进行多准则评分；
4. 对可行方案执行 1,000 次 Monte Carlo 采样，输出得分区间；
5. 输出推荐方案、不可行原因、数据质量警告和翻转条件。

### 价值计算，不虚构收益

```text
累计停机损失 = 功率缺口 × 电价 × 持续时长
风险暴露 = 失效概率 × 失效影响
方案总成本 = 维修成本 + 停机损失 + 安全风险罚项
```

### 当前诚实边界

人员和工单已接数据库；备件仍从故障知识提取，未接真实库存；天气采用缺失告警和降级假设；历史成功率仍需从真实维修结果计算。因此当前状态标为**原型验证**。

### 视觉指令

使用四方案雷达或矩阵，但必须同时显示“可行 / 不可行 / 数据不足”，不要只显示一个最高分。

## Slide 9｜创新三：策略即执行边界 + 恢复证明

### 页面结论

**安全提示不能只写在页面上，必须成为服务器端不可绕过的执行条件。**

### 策略执行链

```text
身份与角色
→ 风险分级
→ 状态机前置条件
→ 确定性策略
→ 人工审批
→ 幂等业务动作
```

### 关键规则

- 未完成恢复验证，不允许关闭 Incident；
- LLM 输出不能直接写入业务状态；
- 高风险动作必须审批；
- 比赛版本禁止真实设备控制；
- 不满足技能要求的人员不能接受特定工单。

### 恢复证明

恢复验证比较维修前后：

- 振动 RMS；
- 温度；
- 功率输出；
- 告警是否复发；
- 健康指数与 RUL（数据存在时）。

输出 `pass / conditional / fail / insufficient_data` 和证据哈希。只有通过策略条件，事件才能进入 resolved。

### 视觉指令

用“红色策略门”拦住直接关闭请求，绿色通路由“审批 + 执行 + 恢复证明”穿过。

## 附录 B｜评委可能追问的三句话回答

### 为什么需要 Agent，而不是普通工作流？

因为异常调查需要根据证据动态选择工具、识别缺失信息、处理多模态冲突并生成候选方案；但安全动作仍由确定性工作流和策略控制。我们将“开放式认知任务”和“封闭式执行边界”组合，而不是让 LLM 自由执行。

### 你们与传统预测性维护平台有什么区别？

传统平台重点回答“哪里可能坏”；我们继续回答“证据够不够、现在能做什么、谁来审批、执行后是否恢复、全过程能否复盘”。核心对象不是一个预测结果，而是一个携带证明的 Incident。

### 当前最真实的不足是什么？

真实库存、天气和 OPC UA 仍未接企业生产系统，多模态会诊和联邦知识处于模拟验证阶段。我们不会把它们包装成生产能力；初赛先证明一条可复现闭环，复赛再用真实接口替换降级数据源。
