# 风调预顺：赛题创新扩展方向与产品路线

> 目标赛道：GOAI Boundless Agents——AI+工业制造  
> 目标：在现有项目上形成评委一眼能理解、能够真实演示、具有工业价值且可继续落地的创新产品。  
> 范围原则：不讨论数据清洗和数据准备；不靠堆技术名词；不建设与主线无关的完整 ERP、MES 或供应链系统。  
> 评估维度：赛题相关度、工业价值、创新辨识度、现有代码复用度、演示效果、可验证性、实施风险。

## 1. 最终判断

项目不应该继续定位为：

> 风机预测性维护大屏 + AI 聊天助手。

这个定位的问题是市场上类似项目很多，容易被评委理解为“数据可视化、模型预测和问答功能的组合”，创新辨识度不够。

建议升级为：

> **风调预顺 WindOps Nexus：面向风电场的自主运维事件指挥系统。**

一句话价值：

> **它不是只预测哪里可能坏，而是把一次设备异常自动组织成可解释、可审批、可执行、可验证、可复盘的运维事件。**

推荐主闭环：

```text
设备事件进入
  → 告警风暴压缩为一个 Incident
  → 多 Agent 建立因果证据图
  → 决策沙盘比较“立即修 / 延后修 / 先巡检”
  → 安全策略引擎判断可执行边界
  → 生成人员、备件、天气、工序完整的维修任务包
  → 人工审批并执行
  → 自动验证运行状态
  → 生成复盘并更新知识
```

这条路线直接贴合官方要求。Boundless Agents 明确不鼓励通用聊天机器人或单点问答，而强调真实用户、真实工作流和可验证闭环；AI+工业制造方向覆盖设备、工单、库存和生产调度等场景。[GOAI Boundless Agents 官方说明](https://www.goaihz.com/en/tracks?track=apps)

## 2. 创新筛选标准

一个方向只有满足以下条件，才进入实施候选：

1. 现有代码至少能够复用 40%，不能推倒重来。
2. 在 3–5 分钟 Demo 中可以被评委直接看见。
3. 能回答“解决了谁的什么损失”。
4. 有成功与失败两种结果，不是固定动画。
5. 能形成测试、Trace、报告或状态变化等客观证据。
6. 不要求连接真实风机控制器才能演示。
7. 不把 LLM 的自然语言输出当作最终事实或执行许可。

评分说明：

- 置信度：我对“该方向有工业和赛题价值”的判断。
- 可执行度：按照当前 React + FastAPI + SQLAlchemy + Agent/Playbook 架构落地的难度。
- 亮点强度：评委在有限时间内能够感知的差异化程度。
- 工作量：单人有效开发小时，不含现有 P0 修复。

## 4. 第一优先级：自主运维事件指挥官

### 4.1 为什么它比“恢复验证”更高级

恢复验证只是事件指挥官的最后一个环节。真正的创新不是多一个验证按钮，而是建立一个统一的 `Incident`，让告警、诊断、决策、审批、工单、执行和复盘都围绕同一个事件协同。

评委看到的不再是多个分散页面，而是一次事故从发生到结束的完整生命线。

### 4.2 最小产品形态

新增“事件指挥中心”页面：

```text
┌────────────────────────────────────────────────────────┐
│ Incident #INC-20260724-001  齿轮箱异常  风险：高       │
├──────────────┬─────────────────────────┬───────────────┤
│ 事件时间线   │ 因果证据图              │ Agent 决策区  │
│ 14:02 告警   │ 振动异常 ─┐             │ 建议 A 立即修 │
│ 14:03 聚合   │ 温度升高 ─┼→ 润滑异常   │ 建议 B 先巡检 │
│ 14:05 诊断   │ 功率偏差 ─┘             │ 建议 C 延后修 │
│ 14:08 审批   │                         │ 风险/成本对比 │
├──────────────┴─────────────────────────┴───────────────┤
│ 安全策略：2 条通过 / 1 条需审批  │ 当前阶段：等待确认 │
└────────────────────────────────────────────────────────┘
```

最小实体：

```text
Incident
- id
- turbine_id
- title
- severity
- stage
- commander_status
- opened_at
- owner_id
- selected_plan_id
- verification_status
- closed_at
```

建议阶段：

```text
detected
→ correlated
→ diagnosing
→ decision_ready
→ awaiting_approval
→ executing
→ verifying
→ resolved / escalated
```

### 4.3 可复用的现有能力

- Fault 和 FaultSignal。
- Diagnosis Orchestrator。
- Agent Task Planner、Playbook 和 Action Gateway。
- WorkOrder、MaintenanceRecord、Notification。
- RUL、HI、维修计划和天气窗口。
- Knowledge Base。

### 4.4 Demo 亮点

- 一个 Incident 聚合 8–20 条相关告警，而不是创建 8–20 个独立故障。
- Agent 说明“为什么把这些告警判定为同一事件”。
- 评委可以从任何结论点开原始证据。
- 事件关闭时能看到完整责任链和处理时长。

## 5. 第二优先级：告警风暴压缩

### 5.1 业务价值

工业设备出现一个根因时，常常会产生多条关联告警。如果系统把每条告警都独立交给人员处理，会造成重复派单、注意力分散和误判。

创新点不是“做告警列表”，而是：

> 把同一时间窗口、同一设备拓扑、同一因果链上的告警压缩成一个可处理事件。

### 5.2 可实现算法

第一版不需要复杂深度学习，可以采用可解释的混合聚合：

```text
事件相似度 =
  0.30 × 时间接近度
  + 0.25 × 设备/部件拓扑接近度
  + 0.20 × 故障规则关联度
  + 0.15 × 指标共同变化
  + 0.10 × 历史案例相似度
```

处理步骤：

1. 以 5–15 分钟滑动窗口收集候选告警。
2. 按风机、部件和指标建立图。
3. 使用阈值或连通分量形成候选事件。
4. Agent 对候选事件命名、总结并提出缺失检查。
5. 人员可以拆分错误聚合或合并重复事件。

### 5.3 可验证指标

- 告警压缩率。
- 事件聚合准确率。
- 重复工单减少率。
- 人工拆分/合并次数。
- 从首条告警到形成可行动事件的耗时。

## 6. 第三优先级：因果证据图

### 6.1 与普通知识图谱的区别

现有知识库更接近“故障百科”。因果证据图面向一次正在处理的事件，节点和边都有明确时间、来源和支持/反驳关系。

建议节点：

- 观察：振动 RMS 升高、温度升高、功率偏差。
- 假设：润滑不足、齿轮点蚀、轴承磨损、传感器异常。
- 检查：油液检查、频谱边带检查、温度传感器交叉验证。
- 行动：降载、安排巡检、创建工单。
- 结果：指标恢复、无改善、出现新告警。

建议边：

- `supports`：证据支持假设。
- `contradicts`：证据反驳假设。
- `requires_check`：结论仍需检查。
- `caused_by`：事件因果关系。
- `resolved_by`：结果与动作关联。

### 6.2 核心交互

- 点击根因候选，右侧只显示支持和反驳该结论的证据。
- 每个结论显示“规则贡献、模型贡献、知识贡献”。
- Agent 不允许直接输出 100% 确定的根因；必须显示未知项。
- 新证据进入后，根因排序可变化，并保留变化历史。

### 6.3 为什么评委会感知明显

绝大多数项目只展示一段 AI 诊断文字。因果证据图能够把“AI 为什么这样判断”视觉化，并且允许评委主动追问和点击验证。

## 7. 第四优先级：反事实维修决策沙盘

### 7.1 产品定义

系统不只给出一个“推荐维修日期”，而是同时计算多个可选策略：

```text
方案 A：24 小时内停机维修
方案 B：先无人机/人工巡检，再决定是否停机
方案 C：降低负载运行 7 天后维修
方案 D：等待下一个低风速天气窗口
```

对每个方案展示：

- 失效风险。
- 预计停机损失。
- 维修成本区间。
- 人员和备件约束。
- 天气可执行性。
- 对其他工单的影响。
- 最坏情况。
- 推荐理由。

### 7.2 算法建议

第一版使用可解释的场景模拟，而不是声称拥有高精度生产优化模型：

```text
方案总损失 =
  计划维修成本
  + 预期故障损失
  + 停机发电损失
  + 延迟风险惩罚
  + 人员/备件/天气冲突惩罚
```

其中：

```text
预期故障损失 = 方案窗口内失效概率 × 故障后果成本
```

应同时显示：

- 推荐方案。
- 次优方案。
- 哪个参数变化会让推荐翻转。
- 不确定性范围。

### 7.3 核心创新

加入“决策翻转点”：

> 如果未来 48 小时风速降低、备件提前到达或失效概率上升到某一阈值，系统会从方案 B 自动切换到方案 A。

这比普通排序更有技术价值，因为它展示了 Agent 能够解释“什么条件改变会导致决策改变”。

## 8. 第五优先级：工业安全策略引擎

### 8.1 产品价值

工业 Agent 的亮点不应该是“什么都敢自动执行”，而应该是：

> 系统清楚知道哪些事情可以自动做、哪些需要确认、哪些绝对禁止。

建议策略分级：

| 风险级别 | 示例 | 行为 |
|---|---|---|
| L0 只读 | 查询指标、检索知识、生成报告 | 自动执行 |
| L1 低风险写入 | 创建草稿、添加备注 | 执行前展示摘要，可单人确认 |
| L2 运维业务变更 | 派工、修改优先级、生成计划 | 需要具备角色权限并二次确认 |
| L3 高风险操作 | 关闭故障、改变关键配置、生成控制建议 | 双人审批或管理员审批 |
| L4 设备控制 | 启停机、改变 PLC/控制参数 | 比赛版本禁止真实执行，只允许沙箱模拟 |

策略例子：

```text
deny if action == "close_incident" and verification_status != "pass"
deny if action == "assign_workorder" and assignee.skill not contains required_skill
require_dual_approval if risk_level >= 3
deny if action.source == "llm" and playbook_id is null
```

实现上可以先写轻量 Python Policy Engine，不必立即引入新服务；当策略数量增加后再评估 OPA。OPA 的官方定位是把策略决策从业务代码中解耦，并以结构化输入产生允许、拒绝或更复杂的策略结果。[Open Policy Agent 官方文档](https://www.openpolicyagent.org/docs)

### 8.2 Demo 必须展示

- Viewer 尝试关闭事件，被拒绝。
- Technician 尝试在验证失败时关闭事件，被策略拒绝。
- Admin 对 L3 动作审批后才可执行。
- 每次策略判断显示命中的规则、版本和理由。

## 9. OPC UA 数字影子网关

### 9.1 要不要做

结论：

> **值得做，但不要做“完整 OPC 管理系统”。**

完整 OPC 平台会涉及证书、发现、地址空间、历史访问、告警事件、写控制、冗余、网络隔离和大量兼容性工作，容易消耗全部时间，却与 Agent 闭环没有形成直接关系。

建议只做：

> **OPC UA Digital Shadow Gateway：设备只读订阅、语义映射、事件触发和受控写入沙箱。**

OPC UA 官方规范支持信息模型、当前/历史值、Alarm/Event、Client/Server 和 PubSub，适合作为设备层到应用层的工业互操作接口。[OPC UA 官方概览](https://reference.opcfoundation.org/specs/OPC-10000-1/4)

风电领域还存在 IEC 61400-25 系列，它专门描述风电场监控与控制通信中的信息模型、信息交换模型和通信映射。因此，项目可以声明“参考 IEC 61400-25 的设备语义”，但没有购买和完整实现标准前，不能宣称通过标准一致性认证。[IEC 61400-25-1 官方说明](https://webstore.iec.ch/en/publication/29062)

### 9.2 最小功能

新增“OT 连接与数字影子”页面：

- OPC UA Endpoint 列表。
- 连接状态、Security Policy、证书状态。
- 地址空间浏览器。
- 风机/部件/测点语义映射。
- 节点实时值、时间戳和质量码。
- Subscription 状态和最后心跳。
- 断线重连和连接事件。
- “只读 / 沙箱可写 / 禁止写入”标签。
- 选定节点触发 Incident 的规则。

最小演示节点：

```text
WindFarm
└── Turbine_01
    ├── Gearbox
    │   ├── VibrationRMS
    │   ├── OilTemperature
    │   └── AlarmState
    ├── Generator
    │   ├── BearingTemperature
    │   └── ActivePower
    └── ControlSandbox
        ├── RequestedMode
        └── AcknowledgeAlarm
```

### 9.3 实施方式

使用 Python `asyncua` 建立：

1. 本地 OPC UA 模拟服务器。
2. FastAPI 后台 OPC Client。
3. Subscription 监听测点变化。
4. 测点到现有风机/部件的映射。
5. 超阈值或组合条件触发 Incident。
6. 所有写操作只发送到 `ControlSandbox`，不得连接真实设备控制点。

`opcua-asyncio` 提供异步 Client、Server、地址空间浏览、Subscription、事件、历史读取和证书加密能力，适合与现有 FastAPI 异步架构做 PoC。[FreeOpcUa opcua-asyncio](https://github.com/FreeOpcUa/opcua-asyncio)

### 9.4 评委演示

1. 模拟服务器把齿轮箱振动从正常值逐步提升。
2. 页面实时显示 OPC 节点值和质量码。
3. 告警聚合器创建 Incident。
4. Agent 进入诊断、决策和审批链。
5. Agent 提议“降载运行”，安全策略判断这是 L4 控制动作。
6. 系统拒绝真实写入，只允许写到沙箱节点。
7. 评委看到工业连接能力和安全边界同时成立。

### 9.5 不应实现

- 不做 PLC 编程。
- 不承诺连接所有厂商风机。
- 不做真实启停机。
- 不做完整 OPC 证书中心。
- 不自称 SCADA 替代品。
- 不自称符合全部 IEC 61400-25 或 OPC UA Companion Specification。

## 10. Agent 飞行记录器与任务回放

### 10.1 产品定义

把每次 Agent 执行录制成可回放任务：

- 用户输入。
- 选择的 Playbook。
- Agent 分工。
- 上下文摘要。
- 工具调用及耗时。
- 权限/策略结果。
- 人工审批。
- 写入前后状态。
- 失败、重试和降级。
- 最终验证结果。

评委可以点击“回放”，按时间轴重新查看一次任务，而不是只能看终态。

### 10.2 技术实现

为每个任务建立：

```text
trace_id
incident_id
parent_span_id
span_name
agent_name
tool_name
input_digest
output_digest
status
started_at
ended_at
token_usage
cost_estimate
error_code
```

OpenTelemetry 的 Trace/Span 模型能够表达父子关系、时间、状态、属性、事件和跨进程上下文，适合为 Agent、HTTP、数据库和异步任务建立统一观测基础。[OpenTelemetry Traces](https://opentelemetry.io/docs/concepts/signals/traces/)

### 10.3 额外加分

在记录器上增加任务质量评分：

- 计划是否合法。
- 是否出现无效工具调用。
- 是否缺少必要审批。
- 是否成功完成。
- 是否使用降级路径。
- 人工是否修改了 Agent 方案。

这能把“我们有 Agent”升级为“我们能测量和持续优化 Agent”。

## 11. 智能维修任务包

普通工单通常只有标题、描述和负责人。建议升级为可现场执行的数字任务包：

- 故障摘要和证据。
- 安全风险和 LOTO 检查项。
- 工具和备件。
- 人员技能要求。
- 天气与停机窗口。
- 标准作业步骤。
- 预计工时。
- 验收指标。
- 现场图片/语音记录。
- 电子签名。

任务包的价值是让 Agent 交付“可执行成果”，而不是交付一段建议文字。

最小版本只需在现有 WorkOrder 上增加：

```text
procedure_steps
safety_checklist
required_skills
required_tools

```

## 12. 多模态巡检会诊

现有项目已经具备无人机页面、叶片图像诊断和截图理解能力，可以组合成：

> 无人机巡检任务 → 图像缺陷检测 → 部件定位 → 与运行异常联合会诊 → 生成现场复检任务。

创新点不是单独展示 YOLO 框，而是让图像证据影响因果图和维修决策：

- 图像出现叶片裂纹，但 SCADA 未出现明显性能损失：建议限制运行并复检。
- SCADA 出现功率偏差，但图像无叶片损伤：降低叶片故障假设权重。
- 图像质量不足：Agent 不下结论，自动请求重拍指定角度。

该方向视觉效果很强，但需要稳定图像场景和跨模态评测，因此建议作为复赛加分项，而不是初赛主线。

## 13. 事故复盘知识飞轮

闭环完成后自动生成：

- 发生了什么。
- 最初假设是什么。
- 哪些证据支持或反驳。
- 采取了哪些动作。
- 哪个动作有效。
- 误判和延迟在哪里。
- 下次应新增或修改哪条规则。

知识更新流程：

```text
Incident 关闭
→ 生成复盘草稿
→ 提取候选知识
→ 与已有知识比较
→ 人工审核
→ 形成新版本 Playbook
→ 在回放场景中重新评测
→ 达标后发布
```

关键原则：模型只能提出候选知识，不能自动把未审核结论升级为正式规则。

## 14. 风机健康数字护照

为每台风机建立跨周期的“健康护照”：

- 当前健康状态。
- 历次重大 Incident。
- 维修和更换记录。
- 模型预测历史。
- Agent 建议与人工决策差异。
- 验证结果。
- 使用过的规则/模型版本。
- 重要证据哈希。

该功能工作量不大，却能显著增强产品长期使用价值，并为评委展示“系统不是一次性 Demo”。

## 15. 推荐组合方案

### 15.1 最推荐：高分平衡方案

产品名：

> **风调预顺 WindOps Nexus——可验证的自主运维事件指挥系统**

组合：

1. IN-01 自主运维事件指挥官。
2. IN-02 告警风暴压缩。
3. IN-03 因果证据图。
4. IN-04 反事实维修决策沙盘。
5. IN-05 工业安全策略引擎。
6. IN-06 Agent 飞行记录器。

优势：

- 场景、Agent、产品、算法、安全和工程六类评分都能覆盖。
- 最大程度复用当前诊断、预测、工单、知识和 Agent 代码。
- 不依赖额外硬件。
- Demo 结构清晰。
- 每个创新都有可测试指标。

综合推荐度：`96%`。

### 15.2 工业连接增强方案

在高分平衡方案上增加：

7. IN-07 OPC UA 数字影子网关。

为了控制范围，暂缓多模态巡检和复杂知识飞轮。

优势：

- 工业现场感和 IT/OT 融合亮点非常强。
- 能证明项目不是只处理静态 API。
- 设备事件可以主动驱动 Agent。

风险：

- 连接、证书和 Subscription 调试可能占用较多时间。
- 如果 OPC 页面与事件闭环没有打通，会变成独立技术展柜，反而降低完整度。

综合推荐度：`88%`。只有核心闭环已经稳定时才实施。

### 15.3 视觉展示增强方案

在高分平衡方案上增加：

7. IN-09 多模态巡检会诊。
8. IN-11 风机健康数字护照。

适合复赛或已有稳定图像演示条件时采用。

综合推荐度：`84%`。

## 16. 72 小时创新实施建议

该 72 小时只针对创新扩展，不包含现有 P0 代码修复。

| 阶段 | 工作量 | 内容 | 交付 |
|---|---:|---|---|
| A 事件骨架 | 12h | Incident 模型、状态机、事件 API、现有 Fault/WorkOrder 关联 | 单个事件能够贯穿诊断和工单 |
| B 告警聚合 | 10h | 时间窗口、部件关系、规则关联、人工拆分/合并 | 多条告警形成一个 Incident |
| C 因果证据图 | 12h | Evidence/Hypothesis/Check/Action 节点和支持/反驳边 | 可交互的因果图 |
| D 决策沙盘 | 14h | 三种维修方案、成本风险计算、决策翻转点 | 方案对比和推荐解释 |
| E 安全策略 | 10h | 风险分级、权限、验证条件、审批和拒绝原因 | 至少两个拦截案例 |
| F 飞行记录 | 8h | Trace、Span、工具耗时、结果状态和任务回放 | 一次任务可完整回放 |
| G Demo 打磨 | 6h | 固定场景、失败分支、引导、录像预演 | 5 分钟稳定 Demo |

- 暂缓复杂决策翻转点：节省约 6h。
- 暂缓完整任务回放 UI：节省约 6h。
- OPC 地址空间只实现一台模拟风机和 6–10 个节点：控制在 18–24h。

## 17. 五分钟决赛级 Demo 剧本

### 0:00–0:30 设备事件进入

OPC 模拟器或内部事件模拟器让齿轮箱振动、温度依次升高，产生 8 条告警。

展示重点：系统接收到的是多条噪声告警。

### 0:30–1:10 告警风暴压缩

系统把 8 条告警聚合成 1 个 Incident，并展示聚合理由。

展示重点：从“告警列表”变成“业务事件”。

### 1:10–2:00 多 Agent 因果分析

数据、知识、排程和安全 Agent 分工，因果证据图逐步生成。

展示重点：支持证据、反驳证据和待检查项。

### 2:00–3:00 决策沙盘

比较“立即维修、先巡检、延后维修”三种方案，展示成本、风险、天气和人员约束。

展示重点：推荐不是固定答案，参数变化会导致方案翻转。

### 3:00–3:40 安全策略和人工审批

Agent 提议关闭事件或发送控制建议，策略引擎拒绝未验证关闭，并将真实控制动作限制为沙箱。

展示重点：安全边界不是 PPT 文案，而是运行中的规则。

### 3:40–4:30 执行与验证

审批维修任务包，生成工单；模拟完成后进行结果验证。

展示重点：验证失败会自动升级，验证通过才可关闭。

### 4:30–5:00 回放与知识沉淀

打开 Agent 飞行记录器，回放工具调用和审批；生成复盘候选。

展示重点：整个闭环可复现、可审计、可学习。

## 19. 明确不建议做的方向

| 方向 | 不建议原因 |
|---|---|
| 再增加一个普通聊天机器人 | 官方明确不鼓励通用聊天和单点问答，且现有项目已经具备助手 |
| 做完整 ERP/库存/采购系统 | 范围巨大，会稀释风电运维主线 |
| 做完整 SCADA 或 OPC 平台 | 工程量远超比赛周期，容易成为孤立功能 |
| 直接让 LLM 控制真实设备 | 安全风险极高，也无法在比赛环境中可信验证 |
| 为了“多 Agent”增加十几个角色 | 角色数量不是评分点；清晰分工和闭环证据更重要 |
| 只做更漂亮的 3D 大屏 | 视觉可加分，但不能替代真实任务闭环 |
| 宣称“数字孪生”但没有状态同步和行为模型 | 容易被专家追问后失分 |
| 堆向量库、消息队列、微服务和大模型 | 官方和技术评审更看重必要性、可替换性和结果，不看工具数量 |
| 自称满足全部 IEC/OPC 标准 | 未做一致性测试或认证时属于过度宣传 |
| 用固定脚本假装 Agent 自主决策 | 可以有确定性 Playbook，但必须诚实说明哪些由规则、模型和人工完成 |

## 20. 最终实施建议

建议按照以下决策执行：

1. 先完成现有代码 P0 修复，保证基础结果可信。
2. 把 `Incident` 和事件指挥中心作为所有创新的承载体。
3. 优先实现告警压缩、因果证据图、决策沙盘和安全策略。
4. 用 Agent 飞行记录器证明系统可观测、可评测、可复盘。
5. 核心闭环稳定后，再加入 OPC UA 数字影子网关。
6. 多模态巡检、数字护照和边缘离线模式放入复赛/决赛路线。

如果只能选一个最有辨识度的创新，不选单独的 OPC 页面，也不选单独的恢复验证，而应选择：

> **“基于因果证据图和反事实决策沙盘的自主运维事件指挥官，并由工业安全策略约束执行。”**

这个组合同时具有工业价值、Agent 深度、算法可解释性、产品展示力和安全可信度，且能够在现有项目基础上逐步实现。
